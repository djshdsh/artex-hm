# Node.js 2026-10-21 安全版本

2026-10-21 发布：**v22.23.4 / v24.22.1 / v26.12.1**（22.x / 24.x / 26.x 三条线），
最高级别 **HIGH**。同批还更新了 c-ares、OpenSSL、SQLite、Undici，以及 **ca-cert（eMudhra 中间 CA 出事）**。

## 0. 授权边界

- 版本核对、代码/依赖面判断、单次 Brotli 解码面探测属允许范围；
- 造崩溃（DoS）演示必须先说明、每目标一次、低峰执行；
- 不得用 TLS 主机名绕过做真实中间人劫持非授权流量。

## 2. 重点三条（怎么实现的 / 怎么做 / 能得到什么）

### 2.1 CVE-2026-111497 —— Brotli 越界写 RCE（最值得关注）

- **本质**：内存安全。Brotli 解码路径上存在越界写，攻击者可控的压缩数据可破坏相邻堆内存。
- **前提**：目标进程**对攻击者可控数据做 Brotli 解压**。常见面：
  - `zlib.brotliDecompress*` / `createBrotliDecompress` 用于请求体（`Content-Encoding: br`）；
  - 解压上传的文件、消息队列 payload、缓存对象、代理转发的响应体；
  - 框架中间件（如 compression/brotli 相关插件反向使用）。
- **怎么做（探测顺序）**：
  1. 找入口：请求头 `Content-Encoding: br`、上传解压、`Accept-Encoding: br` 的自定义响应缓存；
  2. 判活：发一个**合法** br 体，观察是否被解压（返回 200/业务响应 vs 400/乱码）；
  3. 只有确认"服务端解压攻击者数据"后，越界写才有意义；否则这条对目标不成立。
- **能得到什么**：进程内代码执行（Node 单进程即整站/整服务沦陷）；退一步可稳定崩溃（DoS）。

### 2.2 CVE-2026-105482 —— dns.resolve NUL 截断（SSRF 白名单绕过）

- **本质**：解析顺序不一致。校验用的是完整字符串，实际解析在 NUL 处截断 → 校验放行 A，实际连 B。
- **怎么做**：目标若有"URL/域名白名单"（如仅允许 `*.internal.example`），构造 `allowed.example\x00.attacker.tld` 之类的名字，看是否既通过校验又解析到攻击者目标。
- **能得到什么**：绕过 SSRF 防护、绕过出口白名单，进而打内网服务或回连。

### 2.3 CVE-2026-105483 / CVE-2026-106069 —— TLS 主机名校验绕过

- **本质**：证书里的 IP/host 比对逻辑不规范（全角数字、松散解析），导致**不该匹配的证书被认作匹配**。
- **场景**：客户端侧（`https.request`、`fetch`、webhook 回调、代理）——攻击者持有一张"名字对不上"的证书即可冒充目标端点。
- **怎么做**：在授权测试中，用自签/错名证书搭一个端点，让目标应用发起 HTTPS 请求，看是否被接受（默认应当拒）。
- **能得到什么**：MITM / 凭证回传劫持 / 供应链投毒（需要能影响 DNS 或链路，单独不可远程利用）。

### 2.4 其余值得写进报告的

- `CVE-2026-106074`：SEA/快照里熵缓存被固化 → **每个进程的 UUID/随机数重复**，直接影响 token、重置链接、幂等键的可预测性。审计时优先查"用 randomUUID 做安全标识"的地方。
- `CVE-2026-105481`：keep-alive 复用下响应与请求错位，可能造成**响应串包/信息泄露**，队列型服务尤其危险。

## 3. 版本核对（怎么做，最短路径）

```bash
node -v
node -p "process.versions"            # 含 v8 / openssl / nghttp2 等
npm ls --depth=0 2>/dev/null | head
# 容器
docker run --rm <image> node -v
# 代码仓
grep -n '"engines"' -A3 package.json
```

判定逻辑见 `scripts/node_ver_check.py`。

**探针**（需 `--authorized`）：
- `scripts/cve_111497_probe.py` —— 判"服务端是否解码攻击者可控 Brotli 数据"：
  - 默认：对照组三发（合法 br / 明文冒充 br / 明文），合法 br 被处理而冒充被拒 → 解码面成立；
  - `--ratio`：发 14 字节高压缩比流（解压后 200KB 或 5MB），看是否限制解压体积（DoS 面）；
  - `--malformed`：发**截断**小流，只看错误指纹（`ERR__ERROR_FORMAT_BLOCK_SWITCH` 等），不追求崩溃。

公开 PoC 的实现细节、两阶段触发样本特征、版本矩阵见 `reference.md` 第 7 节。

## 4. 报告要点

| 结论 | 证据 | severity |
|---|---|---|
| Brotli 面确认可解压攻击者数据 | 请求/响应 + 解压生效证据 | **high**（若进一步崩溃/代码执行 → critical） |
| SSRF 白名单绕过成立 | 两组请求对比（校验通过 + 实际解析目标） | **high** |
| TLS 校验绕过 | 错名证书被接受的日志/握手记录 | **medium~high**（取决于能否影响链路） |
| 仅版本 < 修复线 | `node -v` 输出 | **medium**，注明"未验证可达性" |

## 5. 修复与缓解

1. 升级到 22.23.4 / 24.22.1 / 26.12.1；
2. 依赖面：c-ares、OpenSSL、SQLite、Undici 同步升级；**ca-cert 要换**（eMudhra 中间 CA 已被攻陷，等同信任链污染）；
3. 无法立即升级：
   - 关掉"对不可信输入做 Brotli 解压"的路径（改 gzip 或限制解压体积）；
   - SSRF 防护改为"解析结果再校验"（resolve → 校验 IP → 用该 IP 连接，禁止二次解析）；
   - TLS 侧显式校验 `socket.getPeerCertificate()` 的 SAN，别只依赖默认 `checkServerIdentity`；
4. 检测：`Server` 头看不到 Node 版本，靠日志/探针/资产清单；容器镜像按 digest 比对。

详见 `reference.md`。
